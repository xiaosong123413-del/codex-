# Goal 大系统需求总览

日期：2026-05-04

## 目标

把本轮 goal 讨论中的长期产品要求集中归档，作为后续执行前的事实来源。

这份文档描述目标行为，不代表全部已经实现。每次开始执行其中一项时，需要先建立对应执行记录，并明确前端、后端、数据流和验证标准。

## 全局原则

- 前端入口和后端能力必须同时设计。新增按钮、菜单、选择器或页面时，必须明确后端接口、读取配置、写入位置、后续消费流程。
- 不能只做前端展示，也不能只做后端能力；任一侧没接上时，执行前必须停下来确认。
- 系统要自动维护知识和个人信息的连接，但低置信度内容必须标记为待确认。
- 检索和回答必须紧扣用户问题，同时检索个人信息和知识信息，再综合判断。

## 个人信息与知识信息

- 需要区分个人信息和知识信息。
- 个人信息来源包括：个人信息档案、闪念日记、任务池、工作台内容、工作日志、课程与个人经历关系。
- 知识信息来源包括：wiki 知识页、方法库、工具箱、案例库、课程资料、沉淀库内容。
- 用户问题本身也可以连接个人信息和知识信息，不强制依赖单独的桥接页。
- 系统需要自动寻找内容“与我”的关联，例如课程资料要自动绑定课程，课程再与用户个人信息绑定。

## 检索与回答

- 检索策略必须同时覆盖个人信息和知识信息。
- 回答前要围绕问题判断哪些个人信息和知识信息相关。
- 不应只把用户输入当成普通关键词搜索；要结合任务、工作、课程、历史记录、方法和工具。
- 所有 wiki 页都需要标签和别名标签，提升检索命中率。
- 标签和别名需要由系统自动维护。

## Wiki、工作日志和 Graphy

- Wiki 页和工作日志页的信息必须互通。
- 工作日志页、任务池、案例库、个人信息之间需要连接。
- 沉淀库里的方法库、工具箱与知识信息密切相关，也要进入连接网络。
- Wiki 页和工作日志页凡是文档类型，都需要支持富文本编辑，并有固定工具栏。
- Wiki 页和工作日志页的所有内容都需要 Graphy 连通。
- compile 流程也要考虑工作日志页，但必须区分哪些是任务记录、哪些是知识来源。

## 任务池、工作台与自动维护

- 系统可以自动从日记、任务、工作日志里提取候选信息。
- 自动提取的内容必须标记为低置信度待确认。
- 任务池、工作日志、案例库、方法库、工具箱不是孤立模块，需要共同进入个人工作系统。
- 任务管理不能只生成任务列表，需要有项目、领域、工作日志和执行现场之间的流转思路。

## 沉淀库、方法库和工具箱

- 沉淀库本身也是一篇总览文档。
- 沉淀库下面挂方法库和工具箱。
- 方法库和工具箱都需要标签。
- 方法库和工具箱都需要验证状态：已验证但成功、待验证、已验证但失败。
- 沉淀库视觉应回到 wiki 文档类型，不应做成割裂的难看看板。

## UI 与视觉

- 除 wiki 文档页外，其他 UI 风格优先向任务计划页统一。
- 后续整体美化方向是克制、清晰、高级，不能牺牲信息密度和可操作性。
- 任务计划页删除“领域与项目推进”，让“AI 智能排期助手”占满主区域。

## 同步与来源

- 前端选择同步文件夹后，后端必须读取同一份配置并实时纳入扫描。
- 不能靠后端写死某个目录来解决来源检测。
- 新增同步入口时，要明确同步源、目标仓库、manifest、compile 和前端弹窗之间的数据流。

## 微信、OpenClaw、Codex、Claude 与 MCP

- 用户希望通过微信让 OpenClaw、Codex 或 Claude 能通过 MCP 服务调用这个应用。
- 微信由个人微信机器人 / OpenClaw 接管。
- Codex 优先。
- MCP 服务目标部署方向是 Cloudflare Worker。
- Cloudflare Worker 不能被描述成能直接运行本机进程；需要本地 bridge 才能转发到本机 CLI / WebUI。

## 多形式输出

- 对话页需要支持输出类型选择，默认文本，也可选择 HTML 或 PPT。
- Wiki 页工具栏需要新增“多样式输出”，点击后出现 HTML / PPT 两个选项。
- HTML 输出后应生成可打开的网页链接。
- PPT 输出后应生成可下载并打开的演示文件。
- 输出内容要自动放入 `wiki/多形式输出/`。
- 输出索引页和源页面要自动双链。
- 输出内容需要支持删除。
- `open-slide` 可作为 HTML / PDF / slide 风格输出参考；原生 PPTX 需要另接生成器或单独确认实现方式。

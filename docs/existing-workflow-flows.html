已有执行沉淀流程

现有机制已经不是单一“目录树”。它把一次执行记录拆成机器凭证、任务卡记录、项目工作日志，以及资源库/案例库/方法库/资料验证记录这些长期沉淀。

人工入口执行记录器：写刚刚做了什么、停在哪、遇到什么、参考了什么。
AI / 服务处理识别任务、工具、链接、问题、下一步；高置信归档，低置信进待处理。
沉淀出口任务卡、Workflow Event、工作日志、资源库、案例库、方法库、资料验证记录。

一条执行记录的主流程

这是已有“执行记录器归档流程”的核心：同一条事件会被拆成三种视图。

人工输入
执行记录器

输入文本、记录类型、可选任务绑定、附件或链接。

→
识别归档

识别任务、当前节点、问题、下一步、工具和资源线索。

置信判断

高置信直接归档；低置信进入 workflow inbox 待确认。

三种视图
Workflow Event

机器凭证。保留事件 ID、匹配领域/项目/任务、置信度。

任务卡 workflowLog

绑定行动层。写入任务卡日志，并更新 lastStop。

项目工作日志

按时间线写入领域、项目、任务、任务 ID、行动和事件引用。

专题沉淀候选

抽取资源、案例、方法、验证记录，等待沉淀或展示。

关键点：用户只需要写执行现场；系统已经有把同一条记录投射到任务、项目和专题沉淀的路径。

任务卡流程

任务卡是行动层和任务层的连接点。它不是完整项目文档，而是承接执行记录。

输入来源 执行记录器文本；可显式绑定 taskId，也可由系统匹配任务。
写入位置 任务池里的任务卡 workflowLog，并同步更新 lastStop。
项目映射 项目 工作日志.md 会补充任务 ID 与 task-pool/<id> 引用，确保任务卡、执行记录器、工作日志指向同一任务。
低置信记录 无法可靠匹配任务时，不强行写任务卡，先进入待处理 inbox。

案例库、资源库、方法库怎么来

这些不是用户手动填目录，而是从执行记录与验证结果中抽取出来的长期沉淀。

资源库

  • 从记录中的工具、链接、附件中抽取。
  • 例：记录提到“夸克浏览器”和教程链接，进入资源候选。
  • 长期位置：wiki/专题/资源库

案例库

  • 从一次完整行动、问题、解决结果中沉淀。
  • 用于回答“这个问题以前怎么处理过”。
  • 长期位置：wiki/专题/案例库

方法库

  • 从解决记录里抽取稳定做法。
  • 证据来源可包含 workflowLog、case、validation。
  • 长期位置：wiki/专题/方法库

资料验证记录

  • 记录资料、教程、链接是否真的有效。
  • 和案例、方法互相支撑，避免资源库只有链接没有验证。
  • 长期位置：wiki/专题/资料验证记录

执行沉淀页流程

这是用户查看沉淀的入口，不是填写入口。

查看路径

点击“执行沉淀”。

→
#/workflow-artifacts

进入执行沉淀页。

/api/workflow-artifacts

读取快照并补齐运行时队列。

展示内容
Workflow Event 事件池

机器事件凭证。

资源候选

工具、链接、附件线索。

验证 / 方法候选

从解决记录中抽取。

长期 Wiki 文件夹

资源库、案例库、方法库、资料验证记录。

当前项目日志还说明：普通 Wiki 文件树不再直接展示这些执行沉淀专题；它们改由工作日志页或执行沉淀页读取展示。

和新想法的连接

已有流程已经支持“只写行动，向上维护”的方向，但界面表达还可以更统一。

行动层 继续保留执行记录器，作为唯一高频人工入口。
任务层 任务卡读取 workflowLog，形成当前判断、卡点和下一步。
项目层 项目工作日志按时间线聚合任务卡和 Workflow Event。
领域层 领域从多个项目日志和专题沉淀中总结趋势，不由用户日常填写。
